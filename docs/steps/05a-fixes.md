## 2. Компоненты
1. **Select показывает подписи.** Везде, где используется `Select` (фильтры списка заявок, схема исполнения в карточке, `currency-select`), выбранное значение должно отображаться подписью, а не значением (`all`, `scheme_alsafi`). В Base UI для этого передаётся `items` в `Select` (см. документацию shadcn для Base UI). Проверь на витрине `/dev/components`.
2. **Хлебные крошки показывают полный путь:** «Заявки / Заявка № 99», «Заявки / Новая заявка», «Настройки / Пользователи». Название последнего уровня страница передаёт сама (через `generateMetadata` или проп в `AppShell`, выбери простой способ и опиши его в `CLAUDE.md`).
3. **«Проводки по заявке» в карточке:** одна строка на проводку. В строке название операции из `messages` («Заморозка», «Корректировка заморозки», «Закрытие заявки», «Сторно»), дата и сумма по счёту клиента. Сумма показывается со знаком: минус значит списание с клиента, плюс — возврат.
4. **Форма заявки на ширине до 640 px:** кнопки внизу на всю ширину, основная сверху. В таблице выбора поступлений добавь колонки «Плательщик» и «Счёт зачисления», а «Остаток» оставь последней колонкой.
5. **Нумерация:** `createId` ведёт отдельный счётчик на каждый префикс, чтобы номера заявок шли подряд (1, 2, 3…). Тесты, завязанные на конкретные id, поправь.

## 3. Валидация денег (`src/modules/shared/schemas.ts`)
Создай общие zod-схемы и используй их во **всех** actions вместо `z.string().min(1)`:
- `moneySchema`: строка, положительное число, не больше 2 знаков после точки или запятой, на выходе нормализуется в `"1234.50"`;
- `rateSchema`: положительное число, до 6 знаков;
- `percentSchema`: от 0 до 100, до 4 знаков;
- `isoDateSchema`: `YYYY-MM-DD`, реальная дата.

Невалидный ввод возвращает `{ ok: false, error }` с понятным текстом из `messages`, а не исключение.

## 4. Правила заявки (`src/modules/payment-orders/actions.ts`)
1. **`submitPaymentOrder`:**
   - **каждое** выбранное поступление проверяется: принадлежит организации клиента, подтверждено, у всех один плательщик и один счёт зачисления;
   - сумма фондирования не больше суммы остатков выбранных поступлений и не больше свободного баланса организации по книге проводок;
   - клиент выбирает банк и счёт контрагента (в схеме ввода добавь `beneficiaryBankId` и `beneficiaryAccountId`), сервер проверяет, что они принадлежат контрагенту, а валюта заявки входит в валюты счёта;
   - дата фондирования — **самая поздняя** из дат выбранных поступлений.
2. **Распределение фондирования по поступлениям.** Вместо `paymentOrderIds: string[]` у поступления храни связку `{ paymentOrderId, incomingPaymentId, allocatedAmountRub }` (в моках это отдельный массив в store, как будущая таблица `payment_order_incoming_payments`). Сумма распределяется по выбранным поступлениям по порядку дат. Остаток поступления = сумма − распределённое на него. Исправь `listConfirmedIncomingPaymentsForOrganization` и всё, что считало остаток.
3. **Файлы при создании.** `submitPaymentOrder` принимает список файлов (метаданные) и создаёт их в той же операции, что и заявку. Отдельные вызовы `addPaymentOrderFile` после создания убери.
4. **`addPaymentOrderFile`:**
   - клиент может грузить в `payment` только при `canClientEditDocuments` в статусе `needs_correction`, а в `closing` — в статусе `awaiting_closing_documents` или при `canClientEditClosingDocuments`;
   - раздел `bank` доступен только менеджеру;
   - в любом случае загрузка запрещена после `closed`.
5. **Расчёты** (`calculateClientCharge`, `calculateCost`) разрешены только в статусах `in_review`, `sent_to_bank`, `awaiting_closing_documents`, `closing_documents_review` и `correction_review`. Набор вынеси в константу рядом с таблицей переходов. В `closed` расчёт возвращает ошибку.
6. **Ключ идемпотентности** корректировки удержания строится из данных, а не из времени: `payment_order_hold_adjusted:{orderId}:{clientChargeRub}`. Повторное нажатие с теми же цифрами ничего не проводит.
7. **`updatePaymentOrderAssignment`:** исполнитель должен быть активным менеджером с доступом к разделу заявок, схема — существующей и не в архиве.
8. **`requestPaymentOrderCorrection`:** хотя бы один флаг `canClientEdit*` должен быть включён.

## Тесты, которые нужно добавить
- Клиент не может создать заявку с чужим поступлением, с неподтверждённым поступлением или с поступлениями от разных плательщиков.
- Сумма фондирования больше остатка поступлений даёт ошибку.
- Валюта, которой нет у счёта контрагента, даёт ошибку.
- Расчёт для клиента в статусе `closed` даёт ошибку, баланс организации не меняется.
- Двойной вызов расчёта с теми же цифрами создаёт одну проводку корректировки.
- Снятие подтверждения с поступления, распределённого на заявку, даёт ошибку.
- Клиент не может загрузить файл в раздел `bank`.
- Невалидные суммы (`"abc"`, `"-5"`, `"1.234"`) возвращают ошибку, а не исключение.
- Заявка, фондированная из двух поступлений, уменьшает остаток каждого ровно на распределённую часть.
