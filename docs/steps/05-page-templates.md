# Шаг 05. Три эталонных шаблона: список, карточка, форма

## Контекст

Прочитай `CLAUDE.md`, разделы 6, 7 и 8.2 в `docs/target-design.md`. Каркас (шаг 03) и компоненты (шаг 04) готовы. Сейчас делаем три экрана, которые станут **образцом** для всех остальных. После этого шага владелец проекта смотрит результат и вносит правки, и только потом делаются остальные экраны. Поэтому качество здесь важнее скорости.

## Задача

### 1. Список: `/manager/payment-orders`

Шаблон «Список»: `page-header` → панель фильтров → `data-table`.

- **Заголовок** «Заявки». Основной кнопки нет: заявки создают клиенты.
- **Быстрые вкладки** над таблицей (`Tabs`, значение в URL): «Требуют действия» (по умолчанию), «В работе», «Закрытые», «Все». У вкладок счётчики.
- **Фильтры:** статус (несколько), организация, исполнитель («Мои» / любой), валюта, период подачи, поиск по номеру инвойса и контрагенту.
- **Колонки:**
  - №;
  - дата подачи;
  - организация;
  - контрагент;
  - инвойс;
  - сумма (`money` + валюта);
  - сумма фондирования, ₽;
  - статус (`status-badge`);
  - исполнитель;
  - маржа, ₽ (видна только менеджерам с доступом к заявкам).
- По умолчанию сортировка от новых к старым, 25 строк. Клик по строке открывает карточку.

### 2. Карточка: `/manager/payment-orders/[id]`

Шаблон «Карточка».

- **`page-header`:** «Заявка № 123», в `meta` статус, организация и дата подачи. Справа **только действия, допустимые из текущего статуса для менеджера** по таблице переходов. Основное действие одно, например «Отправить в банк». Остальные в `outline` или в меню «Ещё». «Вернуть на исправление» открывает диалог с выбором разрешённых блоков (`can_client_edit_*`) и обязательным комментарием.
- **Левая колонка (широкая), блоки `section-card`:**
  1. «Платёж»: инвойс, сумма и валюта, назначение платежа.
  2. «Контрагент и банк»: снимок реквизитов.
  3. «Фондирование»: плательщик, ИНН, счёт зачисления, сумма и дата, привязанные поступления (ссылки).
  4. «Документы»: вкладки «Документы клиента», «Закрывающие», «Банк» (SWIFT, ордер); загрузка менеджером.
  5. «Видимость для клиента»: три переключателя (`Switch`) с подписями.
  6. «Заметка менеджера»: текст, виден клиенту только для чтения.
- **Правая колонка (узкая):**
  1. «Исполнитель» (`entity-combobox` по менеджерам) и «Схема исполнения» (`Select`).
  2. «Расчёт для клиента»: дата исполнения, курс (с подсказкой курса ЦБ на дату из моков), кнопка «Рассчитать». Результат: сумма к списанию и остаток.
  3. «Себестоимость»: дата, курс, надбавка (по умолчанию 0,2%), кнопка «Рассчитать». Результат: себестоимость, маржа, признак применённого минимума. На этапе прототипа расчёт делает простая функция-заглушка с формулой «сумма × (1 + процент) × курс», настоящие калькуляторы будут на этапе 2.
  4. «История статусов» (`status-timeline`).
  5. «Проводки по заявке»: короткий список проводок со ссылкой на журнал.
- Все изменения идут через Server Actions из шага 02, после успеха показывается toast, при ошибке Alert или ошибка у поля.

### 3. Форма: `/client/payment-orders/new`

Шаблон «Форма»: одна колонка шириной около 720 px, разделы `form-section`, кнопки внизу справа.

- **Разделы:**
  1. «Контрагент»: `entity-combobox` по контрагентам организации с пунктом «Добавить контрагента» (открывает `Sheet` с короткой формой); затем банк и счёт. Список счетов фильтруется по валюте, после выбора показываются реквизиты для проверки.
  2. «Платёж»: номер инвойса, сумма (`money-input`), валюта (`currency-select`, только валюты выбранного счёта), назначение платежа (`Textarea`).
  3. «Фондирование»: выбор одного или нескольких подтверждённых поступлений организации (таблица с чекбоксами, колонка «Остаток»). Плательщик и счёт подставляются из выбранных поступлений, сумма фондирования по умолчанию — сумма выбранного, её можно уменьшить.
  4. «Документы»: `file-upload` с типом документа: инвойс, контракт, ГТД, транспортные, другое.
- **Кнопки:** «Отмена» (`ghost`, с `confirm-dialog`, если форма изменена) и «Подать заявку» (основная).
- **Валидация** zod на клиенте и на сервере, ошибки под полями. При первой ошибке экран прокручивается к полю.
- **Черновиков нет:** заявка создаётся только по кнопке «Подать заявку», сразу в статусе `submitted`. После создания открывается карточка клиента `/client/payment-orders/[id]` (пока заготовка) с toast «Заявка № … подана».

### 4. Общие требования

- Строго по разделу 8.2: одна основная кнопка, монохромно, единая типографика и отступы, суммы через `money`, даты через `formatDate`.
- `loading.tsx` для всех трёх страниц со скелетоном по форме контента.
- Ширина менеджерских экранов рассчитана на 1280 px и шире. Форма клиента удобна на 375 px (одна колонка, кнопки на всю ширину внизу).
- Никаких новых раскладок и визуальных приёмов, которых нет в разделе 8.2. Если без них нельзя, остановись и опиши проблему в отчёте, а не придумывай.

## Не делать

- Остальные страницы не трогать: они делаются после приёмки этого шага.
- Не менять `src/components/ui`.

## Как проверить

- Под `manager.full`: список открывается на вкладке «Требуют действия», фильтры и сортировка переживают перезагрузку, клик по строке ведёт в карточку.
- В карточке заявки в статусе `in_review` видны «Отправить в банк» и «Вернуть на исправление», других переходов нет. После перехода статус и история обновились, в списке заявка переехала на другую вкладку.
- Под `client.alfa`: форма не даёт подать заявку без контрагента, суммы и инвойса. Валюта ограничена валютами счёта. После подачи заявка видна менеджеру в списке со статусом «Подана».
- Все три экрана выглядят прилично в светлой и тёмной теме.
- `pnpm check` проходит.

## Что прислать владельцу проекта

Скриншоты трёх экранов (светлая тема, 1440 px) и формы на 375 px, плюс список мест, где пришлось принимать решения, не описанные в задании.
